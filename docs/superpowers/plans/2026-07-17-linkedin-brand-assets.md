# LinkedIn Brand Assets Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce six PNG images (profile picture, cover banner, launch-post graphic — each in dark and light) for The Zha Foundry's LinkedIn Company Page, built from static HTML/CSS in the repo and rendered with Playwright's CLI, so they're reproducible instead of one-off design-tool exports.

**Architecture:** Six standalone HTML files under `brand/linkedin/`, each a fixed-pixel-size "canvas" reusing the real brand SVG marks and the real CSS token values (copied as literal values, since these are static export targets, not live app pages). A shared `shared.css` holds the font import, reset, and the reusable wordmark-lockup rules; each HTML file's own `<style>` block sets that file's exact sizes/positions/colors. A `render.sh` script calls `npx playwright screenshot` once per file at its exact target pixel size to produce the PNGs.

**Tech Stack:** Static HTML/CSS, `@playwright/test` (already a devDependency, provides the `npx playwright screenshot` CLI — no new dependency needed), bash.

## Global Constraints

- No new brand colors, fonts, or marks — every value here is copied from
  `src/styles/tokens.css`, `brand/*.svg`, `src/components/nav/nav.css`, and
  `src/components/hero/hero.css`. Do not invent new hex values.
- Canvas sizes are LinkedIn's official Company Page specs, verified against
  LinkedIn's Help Center (`image-specifications-for-your-linkedin-pages-and-career-pages`):
  logo 400×400px, cover image 4200×700px (6:1). These are **not** the personal-profile
  sizes (300×300 / 1584×396) that most third-party guides describe.
  See `docs/superpowers/specs/2026-07-17-linkedin-brand-assets-design.md` for
  the correction history.
- This is a static visual-asset task, not application logic — there is no
  unit-testable behavior here. "Testing" per task means: render the PNG,
  verify its pixel dimensions are exactly correct, and visually inspect it
  (via the Read tool) against the spec. Do not invent unit tests for CSS
  layout; that would be testing a scenario ("does this rectangle contain
  this rectangle") that provides no real signal beyond what visual
  inspection already confirms.
- Every HTML file must set `html, body { width: Wpx; height: Hpx; }` matching
  its target canvas exactly, so the Playwright viewport screenshot has no
  scrollbar or overflow beyond the intended canvas.
- The wordmark's gate-bracket frame (`::before`/`::after` pseudo-elements)
  must never use the `border` shorthand — only `border-top`/`border-bottom`/
  `border-left`/`border-right` explicitly, one open side each. The `border`
  shorthand sets all four sides at once and will silently re-enable the side
  that's supposed to stay open, breaking the bracket shape. `shared.css` in
  Task 1 is written this way already; if you touch it, preserve that.

### Task 1: Shared CSS foundation

**Files:**
- Create: `brand/linkedin/shared.css`

**Interfaces:**
- Produces: CSS classes `.canvas`, `.wordmark`, `.wordmark-zha`, `.wordmark-stack`
  (and its `span` children) — consumed by Tasks 3 and 4 (profile pictures in
  Task 2 don't use the wordmark, only the bare mark).
- Produces: CSS custom properties consumed per-file: `--bracket-w`,
  `--bracket-color`, `--bracket-size` (set on `.wordmark` by each page that
  uses it).

- [ ] **Step 1: Create the directory and shared stylesheet**

```css
/* brand/linkedin/shared.css */
@import url('https://fonts.googleapis.com/css2?family=Archivo:wght@500;800&family=IBM+Plex+Mono:wght@400;500&family=Big+Shoulders+Stencil+Display:wght@700&display=swap');

* { margin: 0; padding: 0; box-sizing: border-box; }

body {
  font-family: 'Archivo', sans-serif;
  overflow: hidden;
}

.canvas { position: relative; overflow: hidden; }

/* gate-bracket frame around the wordmark lockup — matches .nav-lockup
   on the live site (src/components/nav/nav.css). Each pseudo-element
   only gets the three border sides that stay closed; the shorthand
   `border` property is never used here because it would set all four
   sides and silently close the open side. */
.wordmark {
  position: relative;
  display: flex;
  align-items: center;
}
.wordmark::before, .wordmark::after {
  content: '';
  position: absolute; top: 0; bottom: 0;
  width: var(--bracket-size, 12px);
  border-top: var(--bracket-w, 2px) solid var(--bracket-color, currentColor);
  border-bottom: var(--bracket-w, 2px) solid var(--bracket-color, currentColor);
  pointer-events: none;
}
.wordmark::before { left: 0; border-left: var(--bracket-w, 2px) solid var(--bracket-color, currentColor); }
.wordmark::after { right: 0; border-right: var(--bracket-w, 2px) solid var(--bracket-color, currentColor); }

.wordmark-zha {
  font-family: 'Big Shoulders Stencil Display', 'Archivo', sans-serif;
  font-weight: 700;
  line-height: 1;
}
.wordmark-stack { display: grid; }
.wordmark-stack span {
  font-family: 'IBM Plex Mono', ui-monospace, monospace;
  font-weight: 500;
  line-height: 1;
}
```

- [ ] **Step 2: Verify it's valid CSS with no syntax errors**

Read the file back and manually confirm every `{` has a matching `}` and
every declaration ends in `;`. This file has no runtime to execute on its
own (nothing links to it yet), so a syntax read-through is the correct
verification here — the real test of whether it's *correct* CSS happens in
Task 3, when a page actually renders using these classes.

Note: 225/400 = 0.5625, the same ratio as the mark's own 64×64 viewBox
(36/64 = 0.5625, where 36 is the 50−14 span of the polyline). This keeps the
same proportional margin as the source `brand/stepped-z-copper.svg` — the
reason the mark survives both circle and rounded-square crop without any
stroke touching the edge.

```html
          <stop offset=".68" stop-color="#e07830"/>
          <stop offset="1" stop-color="#8a8078"/>
        </linearGradient>
      </defs>
      <polyline points="14,14 50,14 50,23 38,23 38,32 26,32 26,41 14,41 14,50 50,50"
        stroke="url(#heat)" stroke-width="5" stroke-linecap="square" stroke-linejoin="miter" fill="none"/>
    </svg>
  </div>
</body>
</html>
```

Layout check (do this arithmetic, don't just trust it): headline block spans
from `top: 200px` to roughly `200 + 132*1.05*2 ≈ 477px` — well within the
upper two-thirds of the 700px canvas, and the mark (`top:50%` of 700 = 350px
center, spanning 160px–540px) never enters the bottom 20% (560–700px) or the
bottom-left corner. The headline box ends at `x: 230 + 2350 = 2580px` and the
mark's left edge starts at `x: 4200 − 240 − 380 = 3580px`, so the two
elements never overlap (and the actual rendered headline text is far
narrower than its 2350px container, leaving even more clearance).

The `drop-shadow(0 0 18px rgba(224, 120, 48, 0.45))` value is copied verbatim
from `.hero-mark .mark-heat` in `src/components/hero/hero.css` — that rule
uses a fixed dark-copper glow color regardless of site theme (heat is a
state, not a theme-dependent color, per `brand/README.md`), so both the dark
and light cover banners use this exact same glow.
